Microservice API Design

Plugin de Claude Code que diseña microservicios y sus APIs en Greenfield, Brownfield y Evolution: reconstrucción As-Is, límites y arquitectura hexagonal, contratos, fichas de diseño por funcionalidad, impacto y handoff a la KB y al código.

  • Versión 0.4.0
  • Documentos STD-OKF-001 v1.11.0-stable

Reglas comunes

  • No inventar fuentes ausentes ni evidencias. Declarar la incertidumbre.
  • Un bounded context no equivale obligatoriamente a un microservicio. No se redefine el DDD aprobado.
  • No hay push ni Merge Request sin autorización explícita.
  • Los validadores locales comprueban estructura, no semántica ni identidad del aprobador.

Estados de tarea

PENDING, READY, IN_PROGRESS, NEEDS_REVIEW, DONE, BLOCKED, FAILED. Una tarea llega a DONE solo desde NEEDS_REVIEW, con evidencia y con sus salidas existentes.

Gates

Aprobar un gate exige actor y evidencia. El actor es una declaración que el CLI no autentica.

G0

Fuentes y alcance

Plan, fuentes, repositorio, ref/commit, ADR y KB definidos.

Se aprueba cuando
scope-manifest.yaml tiene fuentes y no tiene missing_sources.

G1

As-Is y límites

Reconstrucción y límites de servicio aceptados. En Greenfield cubre límites y arquitectura.

Se aprueba cuando
G0 aprobado y tareas con entrada G0 en DONE.

G2

Arquitectura y contratos

Arquitectura To-Be y contratos de API y eventos aceptados.

Se aprueba cuando
G1 aprobado y tareas con entrada G1 en DONE.

G3

Impacto y compatibilidad

FDT, análisis de impacto y migración aceptados.

Se aprueba cuando
G2 aprobado y tareas con entrada G2 en DONE.

G4

Handoff y verificación

Handoff a KB y codebase validado y listo para publicar.

Se aprueba cuando
G3 aprobado, tareas con entrada G3 en DONE y codebase-handoff.yaml válido.

Estados de un gate

NOT_READY, PENDING_APPROVAL, APPROVED, REJECTED.

Controles adicionales

FUNCTIONALITY_DESIGN_READY. Control obligatorio al cerrar la tarea FDT, entre G2 y G3. No es un gate G*. Cada funcionalidad del alcance tiene FDT, sin referencias obligatorias sin resolver, con operationId de OpenAPI alineado, fuentes y escenarios verificables, y aprobación humana para publicar. El CLI ejecuta fdt_validate al pasar la tarea a DONE.
Validación de G4. Antes de aprobar G4, el CLI ejecuta validate-handoff: service_id, escenario, KB bajo codebase/, repositorio con proyecto, rama destino, ref y commit, referencias a ADR, artefactos con origen, destino, acción y validación, y aprobación humana requerida. Uso

Requiere PyYAML. No hay ejecución automática de Claude ni integración con GitLab.

# crear un run (greenfield | brownfield | evolution)
python scripts/workflow.py init <run> --scope DSP-001 --scenario evolution --service <servicio> --workspace-root <workspace>
python scripts/workflow.py check <run>

# aprobar gates y mover tareas
python scripts/workflow.py approve-gate <run> --gate G0 --actor '<aprobador>' --evidence '<referencia>'
python scripts/workflow.py transition <run> --task T01 --to READY --actor orchestrator --reason 'G0 aprobado'
python scripts/workflow.py status <run>

# validadores
python scripts/workflow.py validate-contract <contrato>.yaml
python scripts/workflow.py validate-handoff <codebase-handoff>.yaml
python scripts/fdt_validate.py <FDT>.md
python scripts/fdt_validate.py <fdt-manifest>.yaml --manifest

Observaciones

Hallazgos al documentar el plugin.

Resuelto · estándar. Se copió STD-OKF-001 v1.11.0-stable a standards/. Es aditivo: no cambia el perfil de FDT, y los validadores y la plantilla FDT son compatibles.
Resuelto · sigla HCB. La familia de rutas del handoff se llamaba HOF, igual que un tipo aprobado en v1.3.0 (UX/UI Development Handoff Contract). Se renombró a HCB.
Versiones. plugin.json y el pathmap dicen 0.4.0, y el README.md dice v0.3.0.
README desactualizado. Sus comandos usan init runs/demo sin --workspace-root y no menciona validate-handoff ni validate-contract.
Resuelto · prueba. tests/test_smoke.py se actualizó y pasa: 3 escenarios, todas las transiciones, G0 a G4 y validación del handoff.
C4 y EVT. Están en el pathmap, pero ningún archivo del workflow los produce de forma explícita.
Gates por escenario. El mismo código cubre trabajo distinto según el escenario. G1 es "As-Is y límites" en Brownfield y Evolution, pero en Greenfield cubre límites y arquitectura.
